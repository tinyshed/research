# A directory's scan: the walk, the sorted table and the list, on NTFS and ext4

16 November 2026. What a scan of TinyStore's planned external directories
costs, so that its shape and the default of `every` can be fixed. The design
is the book of external directories, not yet in TinyStore's repository: its
sections *Scan*, *What the engine chooses* and *What needs a round before the
code*. The scan measured is that design's: each folder's names read into a
scan-local SQLite table 4096 a transaction, SQLite sorting them in the byte
order of whole paths, a merge in one pass against a list of a row a file, the
differences written 1000 rows a commit, no folder on another file system
entered.

## Environment and reproduction

- **Machine**: AMD Ryzen 7 7700 (8 cores, 16 threads), 31.1 GiB, Samsung SSD
  990 PRO 1 TB (NVMe) holding drive D:, NTFS with 4 KiB clusters. Windows 11
  Pro build 26300. Microsoft Defender's real-time protection on; whether D:
  is excluded could not be read without an administrator. The desktop ran
  an IDE, a browser and chat programs, idle, and two idle containers of
  other projects (0.00 % CPU in `docker stats`).
- **Linux**: Docker Desktop 29.6.2, its WSL2 VM, kernel
  6.18.33.2-microsoft-standard-WSL2, 16 vCPUs, 15.2 GiB; the image
  `rust:1.99.1`, no limits on the container. The fixtures on a Docker volume,
  ext4 on `/dev/sdd` (the VM's virtual disk, a file on the host's C:, not
  D:), never a bind mount.
- **Versions**: Rust 1.99.1 on both; rusqlite 0.40.2, SQLite 3.53.2 bundled,
  built with TinyStore's `LIBSQLITE3_FLAGS` from its `.cargo/config.toml` at
  `defdb639`. No TinyStore code: the harness is std and rusqlite.
- **Harness**: `tinystore/dir-scan-bench/`, in the commit that adds this
  report. The list's connection is opened as TinyStore opens a writer by
  default: 4 KiB pages, WAL, synchronous FULL, a cache of 1 MiB. One
  difference: SQLite's own checkpoint at 1000 frames runs inside the commit
  here, where TinyStore runs it beside the writer, so its cost is in the
  scan's time. The scan-local table is a private temporary database, a
  cache of 2 MiB, its journal off.
- **Fixtures**, generated by the harness from seed 20261116: a media
  library of 10,000, 100,000 and 1,000,000 files (leaf folders of 5–50 files
  at depth 2–4, each folder above with 3–20 folders: 570, 5,571 and 55,015
  folders, paths 101 B on average), and one flat folder of 100,000 files
  (paths 33.5 B). Sizes 0–4 KiB set with `set_len`, times spread over
  2020–2025. 1M files are 2.05 GB.
- **Passes**, each a process of its own: one warm-up walk, then 7 bare
  walks, 5 first scans (each into an empty list), 7 scans that find nothing,
  each followed by the same scan sorting in memory, interleaved, and 5 scans
  after a touch of the time of 1 % of the files (chosen by a hash of the
  path and the pass's seed). Linux then ran the same passes cold, each after
  `sync; echo 3 > /proc/sys/vm/drop_caches` in the privileged container.
- **Order, UTC**: Linux 15:23:49–15:44:37, Windows 15:45:57–15:57:11.
- **Commands**, from the repository's root in Git Bash:

  ```sh
  sh tinystore/dir-scan-bench/round.sh tools     # the Linux binary on a volume
  sh tinystore/dir-scan-bench/round.sh check     # a mount and a link inside a tree, std's syscalls
  sh tinystore/dir-scan-bench/round.sh linux     # ext4, warm and cold
  sh tinystore/dir-scan-bench/round.sh windows   # NTFS, warm
  sh tinystore/dir-scan-bench/round.sh summary
  sh tinystore/dir-scan-bench/round.sh clean     # the volumes
  ```

- **Raw output**: [`data/dir-scan-2026-11-16/`](data/dir-scan-2026-11-16/),
  a JSON line a pass, and `summary.md`, every table below with CPU time.

A first Linux run is not kept: its run.sh dropped the caches in the warm
passes too, so its warm cells were cold. The fix is the guard on `drop` in
`run.sh`; every Linux number here is from the second run.

### 6. The list's file at 1,000,000 files

Identical on both systems to within 4 KiB; after `wal_checkpoint(truncate)`,
from `dbstat`.

| Object            | Pages  | Bytes a file | Payload a row | Unused bytes |
|-------------------|--------|--------------|---------------|--------------|
| `files`           | 34,559 | 141.6        | 122.1         | 15.7 MB      |
| `files_by_change` | 32,533 | 133.3        | 109.1         | 20.5 MB      |
| the rest          | 2      | 0.0          | -             | -            |
| the file          | 67,094 | 274.8        | -             | -            |

`files` is `(directory, path) primary key, size, mtime, change, removed`,
`strict, without rowid`; the path is 101.1 B of a row's 122.1. The index
`files_by_change (directory, change)` is what a cursor follows, and since
the table has no rowid it carries the primary key, the path, again. The flat
fixture's shorter paths make 115.8 B a file. The rows were inserted in path
order, so pages are about 87 % full; a list written in a random order would
be larger, not measured.

## The scan that finds nothing is the walk, the sorted table and little else

Over 1M files warm, pass 3 against pass 1 and 3m in the same run:

| System | Walk   | Sort in memory | Sorted table | The table's share |
|--------|--------|----------------|--------------|-------------------|
| NTFS   | 2.36 s | 2.84 s         | 4.40 s       | 1.56 s, 35 %      |
| ext4   | 2.04 s | 2.54 s         | 3.44 s       | 0.90 s, 26 %      |

The merge against the stored list, read 1000 rows a query, is about 0.5 s
of a million files; the table a folder's names go through is the largest
thing the scan adds. On the flat folder the table costs most: 0.331 s
against 0.148 on NTFS. What it buys is the bound: peak RSS is 6–9 MiB from
10k to 1M files and for one folder of 100k, while the sort in memory takes
6 MiB more for that folder, about 60 B a name, and would take about 60 MiB
for a folder of a million (extrapolated, not measured).

`every: '15m'` over 1M files spends 4.4 s of a core in 900 s warm on NTFS,
0.5 %, and 3.4 s on ext4, 0.4 %. Cold on ext4 it is 12.8 s of CPU in 23.7 s,
1.4 % and 2.6 % of the period in wall time. At 100k files each is a sixth to a tenth of that.

## Windows lists what Linux stats

`strace -c` of a walk of 2,000 files (`check-linux.txt`): std's
`DirEntry::metadata` is one `statx` an entry, 2,113 for 2,000 files and 111
folders, 79 % of the walk's system time; `getdents64` 222 calls. On Windows
`DirEntry::metadata` comes from the listing, so the NTFS walk makes no call
a file: the flat folder walks in 0.079 s on NTFS against 0.191 s on ext4.
The media library walks at about the same speed on both (2.36 against
2.04 s over 1M), where NTFS opens 55,015 folders.

The device check: on Linux a folder's `st_dev` from that same `statx`
against the root's, at no extra call; on Windows the reparse-point
attribute of the listing, since a volume mounted in a folder is one. The
check run mounted a tmpfs over a listed folder and put a link in another:
the scan counted both `skipped`, entered neither, and told none of the 974
files under the mount removed; with both gone the next scan found the list
unchanged.

## Surprises

- The first walk on Windows after the 1M tree was written took 23.9 s, ten
  times the warm 2.4 s. It is the closest to cold Windows came here, but
  what was missing from the cache, or whether Defender was working, is not
  known: it is a hint, not a cold measurement.
- Linux's cold passes spread widely over 1M files (16.5–34.6 s for the walk,
  one pass of 4 at 89.6 s). The VM's virtual disk is a file on the host, so
  "cold" here is the VM's cache dropped while Windows may still hold the
  disk's blocks: a real disk cold would be slower, not faster.
- The 100k library's first scan on ext4 spread 2.4–4.8 s while the flat
  100k took 0.77 s for the same 100 commits; the library's paths are three
  times longer, so more pages a commit, a hypothesis no second measurement
  separated.

## Not measured

- **Cold on Windows**: NTFS's cache of the MFT and the folders cannot be
  dropped without a reboot or an administrator's tool; warm only.
- **APFS and an SMB share**: no Mac and no share here.
- A real disk cold on Linux (see above), a list written in a random order,
  and a folder of a million files.

## What follows

- `every: '15m'` is cheap at a million files warm; the default can stay a
  period of minutes, not seconds.
- The sorted table costs 35–55 % more than a sort in memory, 26–35 % of the
  scan, and is worth it where folders may be huge; a hybrid, sorting in memory up to a few thousand names and
  spilling to the table beyond, would take most of that back. A choice for
  the owner.
- The index by change number repeats the path and doubles the list; a
  rowid table with the path in a unique index, or a change number that
  points at a rowid, would take about 100 B a file from it. Not measured.
