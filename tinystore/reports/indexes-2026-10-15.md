# FTS5 and R*Tree: write/WAL cost and the rebuild boundary — 15 October 2026

Keep SQLite's FTS5 and R*Tree as the starting point. The important unfinished
algorithm is rebuilding beside the old index **with bounded writer occupancy**.
“Run rebuild in the background” is insufficient: a second thread still uses
the file's one SQLite writer. This round measures a monolithic second-index
build with an old reader alive and proposes, but does not implement, a
frontier-based chunked build.

| Question                                          | Answer from the probe                                                              | What follows                                                           |
| ------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Does an index change only query speed?            | No: insert/update/delete, file occupancy and WAL all change.                       | Account for each b-tree and keep a plain-table control.                |
| Can old readers continue during rebuild?          | Yes, in WAL mode in this probe.                                                    | Do not confuse read continuity with write availability.                |
| Can a held reader prevent reclaiming rebuild WAL? | Yes; checkpoint progress is recorded while it holds the old snapshot.              | Admit rebuild against WAL/disk headroom and reader age.                |
| Is dual index maintenance correct automatically?  | Only if triggers and the backfill frontier agree on which rows the new index owns. | Build/switch needs its own atomic state machine and correctness tests. |

Synthetic fixture: 100k rows, `id INTEGER PRIMARY KEY`, deterministic body

all cases; the fixture is generated by source, not a committed corpus.
The token fields repeat every 1000 rows, and coordinate pairs repeat every
10000 rows (ten rows per distinct point). This repeated vocabulary/geometry
is a specific synthetic shape, not a diverse real-document corpus.
Insert batches contain 1000 rows. Update the first 10%, then delete the first
10%, each in batches of 1000. WAL is measured live before each explicit
TRUNCATE checkpoint, and dbstat assigns actual b-tree pages after insertion.
No VACUUM follows deletes; free pages are not counted as an index saving.

Three passes rotate plain/FTS/R*Tree order, one fresh process/file per case,
no excluded warmup. The plain table, FTS external-content table and R*Tree all
store the same base rows. Triggers maintain indexes in the same transaction.
FTS queries count a literal tenant token; the plain LIKE query checks the
same prefix token boundary. R*Tree uses a coordinate rectangle with integer
bounds and measures a **different predicate**. Its query latency is not a
spatial speedup versus the LIKE control. All query counts/checksums are raw.

The rebuild creates `_next` virtual tables and dual-maintenance triggers in
one IMMEDIATE transaction, then bulk-populates `_next`. A dedicated old
reader starts/reads its snapshot before rebuild, keeps querying it during
the build and must see the same count. PASSIVE checkpoint stats are captured
before releasing it. Afterward, 1000 singly committed inserts maintain both
generations and their query results are compared. That measures dual-write
latency, not a matched single-index overhead ratio.

These results apply to this synthetic vocabulary, coordinate distribution,
batch size and virtualized disk. They do not establish production search
capacity, language/tokenizer quality, geo precision, or how a million-row
customer fixture behaves. Rebuild code is intentionally small and does not
include the product authorizer, migrations, schema hashes or wire encoding.

On this fixture, insert WAL grows from 12.35 MiB without an index to
34.93 MiB with FTS and **209.67 MiB with R*Tree** in every pass. The R*Tree
is not remotely that large on disk: this is repeated page logging across
the 1000-row transactions, not retained payload volume. The spatial fixture
walks a deterministic dispersed insertion order. Do not generalize this
amplification to every coordinate order or batch size; those controls are
not run here. It is enough evidence to include geo maintenance in future
replication/WAL admission measurements.

The transaction's duration is a **writer exclusion interval**: another
writer cannot begin until it ends, even though old readers continue. The
probe does not enqueue a second writer or measure its p99, so it does not
claim a measured concurrent-write stall distribution. The exclusion follows
from SQLite's one-writer transaction held around the measured rebuild.

PASSIVE checkpoint can return `busy=0` and still checkpoint none of the new
frames because an old reader pins them. Use the log/done frame counts and
live WAL bytes, not the busy field alone. A long reader plus a large rebuild
can exhaust WAL/disk budget. WAL bytes here are native SQLite WAL growth,
not a measured replication feed, network egress or replicated apply cost.
Do not multiply these bytes by an unmeasured replica policy and call that a
measurement.

The old and new indexes agree after the 1000 post-build inserts. FTS5's
integrity-check command and SQLite integrity_check pass. The R*Tree check
compares the old/new rows for this fixture; it is not a generalized geometry
or crash-during-switch test. Rebuild remains monolithic and no switch is
implemented in the probe.

## Proposed chunked build algorithm

Use the file's existing writer and schema registry, not a competing SQLite
writer connection or a long-lived backfill snapshot. A candidate state is:

```text
index_generation(id, definition_hash, state, high_watermark, frontier)
state: preparing -> building -> active -> retiring
```

1. In a short writer transaction, create the new virtual table, capture
   `H = max(document_id)`, persist frontier `F` as “no rows covered” initially,
   and install its maintenance triggers. Use an explicit empty/nullable state,
   not `min(id)-1`, which can overflow. An empty source has no backfill. The
   old generation stays active.
2. The new generation's triggers own rows satisfying **id <= F or id > H**.
   Backfill owns the yet-unbuilt interval **F < id <= H**. Insert/update/delete
   triggers must apply this predicate separately to OLD and NEW ids. A change
   of rowid can cross the frontier in either direction.
3. For each bounded writer transaction, read a short next chunk from the
   authoritative documents, add those rows to the new index, and advance F
   in the **same** transaction. No concurrent writer can change a selected
   row between its read and that commit. Deleted holes do not block progress;
   when no rows remain in the interval, advance F to H. Yield between chunks.
4. New rows above H are indexed immediately; inserts into holes below F
   are indexed immediately. Updates to the unbuilt interval wait for the
   backfill to see the latest authoritative value. This avoids duplicate
   insertion and stale FTS postings from a naive always-dual-write trigger.
5. At F=H, validate the generation and atomically change the registry's
   active generation/hash. Invalidate or version prepared query handles.
   Keep the old generation until old query handles can no longer target it,
   then drop it with bounded disk/WAL admission.

The predicates above treat an empty F as negative infinity. A registry switch
also assumes index access resolves through that registry. Arbitrary SQL that
names a virtual table directly needs a stable SQL name and a separately
verified rename/facade/schema-invalidation protocol; changing a registry row
alone does not rewrite those statements. That public SQL naming contract is
another implementation decision, not solved by this probe.

FTS external-content DELETE needs the **old indexed text** supplied to its
special delete command. Updating new content without removing old tokens can
leave stale results even if a row count looks plausible. R*Tree bounds use
outward-rounded 32-bit floats: prefer overlap as a candidate predicate and
refine against authoritative coordinates when exact geometry is promised.
The integer-bound point fixture here does not validate arbitrary boundary
precision, antimeridian wrapping, poles, polygons or geodesic distance.

Generate maintenance only for indexed-column changes, with null-safe OLD/NEW
comparisons. Re-tokenizing text because a coordinate changed, or rewriting a
spatial node because an unrelated status column changed, is unnecessary
writer/WAL work. This probe updates both text and coordinates deliberately;
it does not measure that column-specific trigger optimization.

This frontier scheme assumes a stable ordered integer document key and
same-file triggers. For other keys or cross-file data, design a separate
mapping/delta protocol; do not silently extend the proof. A crash must either
roll back a chunk/frontier together or reopen its recorded state. Definition
changes during a build must cancel/restart a generation explicitly. A slow
or paused build still incurs writes for its covered rows and consumes disk.

Chunk size should be governed by writer-time/dirty-byte budget and current
load, not merely a fixed number of rows: FTS token count varies sharply.
The current scaling research already distinguishes WAL admission from a
strict bound on an arbitrary SQL transaction. Rebuild must obey that same
envelope, reader-age policy and free-space guard, and pause before starting
another chunk when the reservation is unavailable.

## What follows

The next experiment must run mixed reads/writes **during** chunked backfill,
delete and move keys across F/H, kill after each state transition, verify
search equivalence to a clean rebuild, measure foreground writer p99 and
break down both generations' file/WAL growth. Until that gate passes,
“background rebuild without stopping writes” remains a proposal. Vector
search and a custom search engine are outside this round.
