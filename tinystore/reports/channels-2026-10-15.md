# Ephemeral Channels: fan-out, gaps and path subscriptions — 15 October 2026

Use a shared bounded event log with subscriber cursors as the design baseline.
This round does not justify a custom lock-free buffer. The mutex ring prototype
has no demonstrated advantage over Tokio broadcast at 1000 subscribers; both
avoid a queue allocation per recipient, while bounded queues spread the work
into publication and retain a separate backlog of references per subscriber.
These are standalone in-process prototypes, not TinyStore or SDK throughput.

| Question                                   | Answer                                                                                             | What follows                                                                             |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Does publish/s describe delivery capacity? | No. Shared logs can overwrite almost the entire burst while reporting millions of publishes/s.     | Report delivered fan-out, loss and delivery latency together.                            |
| Must a subscriber own a payload copy?      | No. All three candidates share an immutable Arc payload.                                           | Separate payload sharing from the choice of queue algorithm.                             |
| Can sequence jumps alone implement gaps?   | No. Drop-new queues lose their final tail without another message to expose it.                    | Keep publisher watermarks or an independent sticky gap state.                            |
| Are path subscriptions feasible?           | A segment trie routes the synthetic exact-plus-prefix workload without scanning all subscriptions. | Define literal exact/subtree semantics before adding wildcard languages.                 |
| Does after-COMMIT imply commit order?      | No. A deterministic two-thread witness delivers B before A after A committed first.                | Append to an ordered bounded handoff at the writer boundary if commit order is promised. |

The candidates have different overflow policies: ring/broadcast overwrite
the oldest event and retain a recent tail; try_send queues drop the new event
and preserve an old backlog. Faster queue publication is not equivalent
semantics. A delivered-only p99 also has survivorship bias when most events
were dropped. The explicit producer yield every 32 publications is a workload
choice, not a property of a production scheduler.

The custom ring is intentionally simple: it enables a Notify waiter on every
receive before checking the buffer, even when data is already available.
An empty-buffer fast path could avoid that work; it is not tested here.
The comparison rejects this prototype as a reason to replace broadcast,
not every possible optimized shared-ring implementation or the ring algorithm
as a class. Any later optimization must be compared in a new paired run.

The 4-slot deterministic overflow check publishes ten messages before
reading. Broadcast and ring return six lost and four delivered; the queue
delivers four and observes **zero** lost from sequence gaps, although the
publisher rejected six. Keep a sticky interval `[first_missing, next)` outside
the ordinary message queue. Flush it before retained data, including when no
new publication follows. Merge repeated gaps; a full queue must never drop
the only evidence that its data was dropped.

One thousand forced ring wait/register schedules complete under a timeout.
The prototype enables its Notify waiter before checking head/closed state;
`notify_waiters` stores no permit for a future waiter. This is a targeted
race check, not a proof of all interleavings or a substitute for Loom.

## Proposed algorithm and SDK surface

This is a proposal, not an accepted API:

```ts
const sub = await store.channels.subscribe('tenants/acme/orders', {
  scope: 'subtree',
}) // await confirms registration; default scope is exact

for await (const event of sub) {
  if (event.type === 'gap' || event.type === 'reset') {
    await reloadOrders()
    continue
  }
  applyIfNewer(event.data)
}

await store.channels.publish('tenants/acme/orders/42', {
  version: 17, status: 'paid',
})
```

Exact `orders` matches only `orders`; subtree `orders` matches that path and
`orders/42`, not `orders-old`. Split literal segments at `/`; choose and test
empty-segment, Unicode and length rules once. No glob, regex, URL decoding or
implicit parent traversal is needed. A read capability must be checked at
subscription admission; paths themselves are not tenant authorization.

Use a trie from path segments to **active selector groups**, with an exact
group at a leaf and subtree groups at ancestors. A group owns one byte- and
count-bounded ring shared by every identical selector. Publish once into
each matching group, sharing the same immutable event/payload; never scan all
subscribers to discover matching paths. This changes retention work from
one queue per subscriber to one log per distinct active selector. Publication
still has wakeup/fan-out work proportional to interested sessions: the
prototype does not prove O(1) total delivery.

A subscriber owns `(group, epoch, next_seq)` and a sticky gap/reset state.
If its cursor is older than the group's retained start, first return a gap,
then the retained tail. A new subscription starts at head, not at zero.
Disconnect/restart creates a new subscription and reset; no `from:last-seen`,
ACK retention, replay guarantee or durable history is implied. Sequence
numbers are local to a selector epoch; they are not a Records cursor or a
database snapshot version. Two separately requested overlapping subscriptions
are two streams; define duplicates before adding a combined-selector API.

Use fixed slots and a mutex first. Shared payload allocation is O(publications),
not O(recipients); Arc clones and receiver wakeups still cost CPU. No custom
unsafe/lock-free algorithm follows from this round. TinyStore's core is
runtime-neutral: Tokio here is a reference implementation, not a reason to
require a Tokio runtime of Rust callers. Reuse callback/waker style handles
already used by job watches, with bounded work per ready session and wake
coalescing. Bound selector count, subscriber count, path bytes, event bytes,
transaction staging bytes and global retained bytes; a root wildcard must not
turn a cheap producer into unlimited memory growth.

The measured payload is made as Vec then converted to Arc, and Event has
another Arc allocation. There are publication allocations and a Vec-to-Arc
copy; none is per subscriber. An initial prototype comment saying “one
allocation” is not an allocation measurement and is corrected in the final
source documentation. This round does not count allocator calls.

## COMMIT and transport traps found in the current architecture

The current `Transaction::after` hook is an appropriate starting seam, but
its hook vector is transaction-wide, not savepoint-scoped. Event staging must
mark its length/bytes at every call/savepoint and truncate on rollback.
Registering a callback before a call can fail would otherwise leak a rolled
back publication. The existing Jobs callers are wakeups, not an event log;
this is an extension trap, not a claim that Jobs currently emits false data.

The hook is currently compiled under the Jobs feature. A Channels feature
must expose the shared transaction seam without depending on the Jobs engine
being enabled, and pass a Channels-only feature build. File ownership and
rollback machinery stay below either engine.

The deterministic probe checks outer rollback, savepoint rollback and a
deferred-FK COMMIT failure. No events escape those paths. A second probe
commits A, stalls A's return callback, commits/publishes B, then releases A:
delivery is B,A. Therefore either promise **publication order only**, or
append committed event batches to a bounded handoff while each file's writer
still owns commit order, after SQLite says success and before handing off the
writer. Wake subscribers outside that boundary. Do not invoke SDK callbacks,
socket writes, serialization or arbitrary user code on a SQLite writer.
Across files there is no SQLite transaction or natural global commit order.

Reserve staging and handoff memory before mutating durable data. An error
allocating a channel notification after a successful durable COMMIT cannot
roll that commit back. A committed transaction followed by process death
before dispatch may lose notifications: this is consistent with ephemeral
Channels. An indeterminate COMMIT outcome is not the deterministic rollback
tested here; recovery/snapshot refresh must handle persisted changes without
a notification. SQLite commit/update hooks do not supply a durable outbox.

`wire/session.rs::queue` encodes frames into an expanding `Output.bytes`.
Its `KEPT` constant shrinks capacity after draining; it is not a queue bound.
Existing config/job watches gate DATA with stream credit before calling
`link.send`. Channels must do the same and also bound the **connection's
aggregate** queued bytes. Stream credit times 1024 streams can still be a
large connection budget. Credit is returned when the SDK consumer advances,
not immediately after bytes enter another unbounded JS/Python queue. A slow
connection accumulates at most its reserved byte budget and a sticky gap;
it never pins old log payloads indefinitely.

The registration response must precede DATA. For snapshot-plus-notifications,
subscribe and await registration first, then read the authoritative snapshot,
then apply versioned events. A gap or reconnection restarts this procedure;
an unversioned snapshot plus an unversioned event stream is not a loss-free
handoff. Channels wake Records/Jobs consumers; they do not replace their
durable source of truth.

## What follows

Implement a runtime-neutral shared bounded log and literal selector router,
using the standard broadcast semantics as the behavioral baseline. Preserve
explicit gaps and byte credit from the start. Before selecting a custom
buffer, measure the complete protocol/SDK path, zero-credit receivers,
subscription churn, many active channels, mixed engine writes, cancellation
and actual snapshot recovery. Multi-publisher ordering, transport throughput,
zero allocations per publish and multi-host delivery are not proved here.

Reference behavior is
[Tokio broadcast](https://docs.rs/tokio/1.53.2/tokio/sync/broadcast/index.html);
the report's version is locked in Cargo.lock. The prototype's explicit
overflow checks establish the observed retained/lost counts independently
of documentation prose.
