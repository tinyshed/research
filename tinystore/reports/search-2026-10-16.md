# TinyStore Search: multilingual analysis and storage — 16 October 2026

**Declared Search measurement suite complete.** Seven binary profiles, all 54
natural-query runs, 12 analyzer samples, four concurrent-write runs, four 100k
scale controls and eight authoritative-store runs at 100k/1m are published.
Twelve small gold diagnostics and separate lifecycle/namespace checks are
retained. This closes this Search evidence suite, not the paused older Index
sweep or product implementation gates. A reproduced token-namespace defect
means the measured analyzer must not be copied into product code unchanged.

The product requirement is zero-configuration multilingual **Search**, distinct
from a universal secondary Index Engine. The previous recommendation against
the latter does not reject the former. Product Core/public API are unchanged.

The recommendation is a shared, versioned text analyzer with explicit ownership
boundaries: same-file FTS5 for an SQL projection; Tantivy as the leading
standalone read-oriented candidate when its higher memory and commit costs fit
the agreed budget. FTS5 remains the simpler standalone candidate for workloads
that prioritize small memory and frequent individual commits. The data does not
support choosing one backend from binary size or isolated query/s alone.

## What is being compared

[`search-lab`](../search-lab/README.md) installs an actual Rust FTS5 tokenizer
through SQLite's C API and a Tantivy Tokenizer over the same analyzer. Both
index title/body with full positions/frequencies and execute literal OR-of-word
top-10 ranked queries. No LIKE/MATCH equivalence, phrase/ranking equivalence,
translation or semantic-neighbour guarantee is assumed. Raw user text is not
interpreted as query syntax. BM25 defaults, field normalization and synonym
scoring can produce different ranks even with identical term membership.

The shared pipeline is ICU4X word boundaries, per-original-span NFKC/lowercase,
ё→е, then raw surface forms plus tagged colocated stems. Original byte offsets
are retained for highlighting. `auto` uses RU for Cyrillic and EN for Latin;
this is a controlled three-language candidate, not complete morphology for
every Cyrillic/Latin language. Other scripts use ICU segmentation.

Controls separate ICU-only, naive field-language detection, all-language
EN/DE/FR/ES stem expansion, and a hybrid storing one detected-language stem
while expanding short query terms. A deliberately simple whole-text Jieba
control tests a different segmentation integration. Its multi-position query
expansion has different phrase/OR behavior between the two adapters: it must
not establish a matched cross-engine speed/quality claim. Its failure on short
RU/EN words and compound Chinese words is evidence about this integration,
not a verdict on a correctly integrated search-mode Jieba or Lindera.

## Binary budget is feasible, but it is not the whole cost

Same native Linux x86-64 research CLI, release opt-level=3, thin LTO,
codegen-units=1, stripped symbols:

| Build profile | Whole ELF MiB | Additional MiB over SQLite baseline |
|---|---|---|
| SQLite baseline | 2.458 | 0 |
| FTS5 + ICU compiled segmentation data | 4.885 | 2.427 |
| FTS5 + ICU + RU/EN/DE/FR/ES stem code | 4.963 | 2.505 |
| Above + Whatlang | 5.217 | 2.759 |
| Above + embedded Jieba | 7.943 | 5.485 |
| Tantivy + same ICU/stem analyzer | 8.486 | 6.028 |
| All experimental features | 11.712 | 9.254 |

These are measured whole executables, not predicted increases to the TinyStore
product/FFI binary. Main timings use the all-feature CLI; separate slim profiles
measure deployment size. ICU dictionary/LSTM data and optional classifier/Jieba
data are already embedded; there is no runtime download in these prototypes.
Jieba's compressed binary data still requires runtime initialization/RAM.
No Lindera dictionary binary has been measured; do not attach an invented size
to its Japanese/Korean/Chinese options or treat them as evaluated defaults.

Analyzer throughput on the same sampled mixed text is 11.73/14.29 MiB/s ICU,
8.29/7.22 `auto`, 3.15/3.53 naive language detection and 2.87/3.55 hybrid.
The naive Jieba control initializes in 235/118 ms and adds 32.66/32.58 MiB RSS.
ICU/auto initialization is small, but its initial RSS delta is not the complete
resident model cost: compiled data is demand-paged and tokenization warms it.
Models should be shared across connections; loading a dictionary per reader
would multiply its memory cost.

## Quality is measured on judged natural queries

The pinned [NoMIRACL dataset](https://huggingface.co/datasets/miracl/nomiracl)
provides natural MIRACL questions and human relevance judgments. This round
deduplicates identical passage IDs, retains 25,086 RU / 31,263 EN / 31,826 ZH
documents and selects 200 dev questions/language by SHA-256(query ID).
The mixed collection has 88,175 documents and 600 questions. It is the released
judged passage pool, including dev/test distractors, **not** full Wikipedia.
There is no model training on these questions.

The Chinese upstream pool lacks 32 qrel document references, including 13
positive references. Queries with any missing judged document are excluded
before hash sampling; all omissions and duplicate counts are retained in
`corpus.json`. This limitation prevents presenting the sample as the complete
MIRACL dev benchmark.

Collection retrieval treats unjudged items as zero for conventional nDCG/MRR,
and reports their coverage. They are not confirmed false positives. A separate
query's judged-pool rerank measures quality over its human-labelled candidates;
it must not be confused with searching a large collection. Known negatives,
Recall@10, MRR@10, nDCG@10 and every returned ID are retained.

Completed results reject two shortcuts. RU ICU-only does not outperform
native Unicode61 overall; `auto` restores useful morphology but has errors.
In the first 200-query ZH pass, native Unicode61 Recall@10 is 0.005 versus 0.597
for ICU: segmentation matters far more than choosing an inverted-index library.
Conversely, Tantivy's matched ICU ranked top-10 latency is much lower than
FTS5's in the completed RU passes. The earlier single-term/full-result-set
index study did not establish this workload's economics.

All paired values, CPU/RSS, index objects, source bytes, WAL and quality are in
[the measurement tables](search-measurements-2026-10-16.md). Each declared cohort
has both passes; no missing result is filled with an extrapolation.

On the mixed 88,175-document collection, 600 natural questions, pass 1; pass 2:

| Same `auto` analysis | Build s | Top-10 ID query p99 ms | Query/s | Index MiB | nDCG@10 | Recall@10 |
|---|---|---|---|---|---|---|
| FTS5 | 20.15; 16.85 | 225.780; 168.015 | 22.1; 23.0 | 69.4; 69.4 | 0.5109; 0.5109 | 0.6969; 0.6969 |
| Tantivy | 15.27; 17.60 | 6.453; 4.009 | 872.0; 955.4 | 51.7; 51.7 | 0.5040; 0.5040 | 0.6844; 0.6844 |

A paired 2,000-resample query bootstrap gives FTS5 minus Tantivy nDCG@10
difference +0.00689, percentile 95% interval **−0.01274 to +0.02641**. It does
not establish a quality winner. This resamples the fixed released passage-pool
queries, not arbitrary languages or a full-Wikipedia population. Seed, code
and output are in `audit.py` and `postflight-audit.json`.

These are postings plus a common separate SQLite source. They do not compare
whole independent collections. Multi-language stem expansion increases FTS
index size to 116.2 MiB and Tantivy to 83.9 MiB without improving nDCG here.
Detection/hybrid also show no relevance improvement over `auto` on these three
language groups. This does not evaluate German/French population relevance.

The ranked-query gap is measured for this OR-query pipeline, including common
terms. Query pruning/stopword handling, selective planning and alternative
FTS query formation may change it; no causal isolation proves FTS5 cannot be
improved. Matched membership controls prevent attributing the speedup to
silently dropping matches. They do not imply identical scoring or query work.
The controls compare count and ID checksum for the first 12 questions in each
of 20 matched scenario/pass groups; they are not exhaustive equivalence for
every possible query. Jieba is excluded for the stated semantic difference.

## Standalone collections must pay for original documents

[`search-store-lab`](../search-store-lab/README.md) compares contentful FTS5
with a key/id map against Tantivy with stored key/title/body and indexed keys.
Each backend is authoritative: there is no secondary SQLite source for Tantivy.
Both hydrate actual top-10 fields under one statement/Searcher snapshot. This
is a different, explicitly measured contract from indexing an SQL table.

At 100k mixed documents, pass 1; pass 2:

| Owned collection | Bulk upsert import s | Stored backend MiB | Hydrated query p99 ms | Single SET p50 ms | Single SET p99 ms | Process HWM MiB |
|---|---|---|---|---|---|---|
| FTS5 | 28.14; 24.32 | 193.4; 193.4 | 135.066; 118.623 | 1.051; 1.017 | 22.145; 23.769 | 193.2; 193.4 |
| Tantivy | 19.88; 25.23 | 116.1; 116.1 | 4.257; 5.758 | 24.367; 15.979 | 246.224; 52.784 | 458.9; 442.8 |

The query sample here is the first 60 natural **RU** questions over mixed
RU/EN/ZH documents, not a balanced multilingual p99. Individual SET/DELETE
has 100 samples/pass on the first 100 RU documents. One 100-document commit
per phase/pass is a batch-cost diagnostic, not a measured p99 or steady load.
SQLite checkpointing is outside operation latency; Tantivy commit/reload is
inside it, with normal background merging.

At one million repeated-pool documents, pass 1; pass 2:

| Owned collection | Bulk upsert import s | Stored backend MiB | Hydrated query p99 ms | Single SET p50 ms | Single SET p99 ms | Process HWM MiB |
|---|---|---|---|---|---|---|
| FTS5 | 303.72; 247.65 | 1777.8; 1777.8 | 1474.205; 1144.953 | 1.400; 1.260 | 26.880; 25.365 | 1031.9; 1032.0 |
| Tantivy | 286.95; 216.55 | 1014.1; 1014.1 | 67.579; 47.364 | 41.219; 20.555 | 213.078; 99.301 | 2474.2; 2469.1 |

One observed 100-document SET commit takes FTS5 63.434; 57.512 ms versus
Tantivy 78.878; 40.667 ms: this motivates grouped writes, but one batch/pass
cannot establish its sustained throughput or p99. FTS bulk-import WAL reaches
1788.2 MiB before checkpoint, with another 9.79; 6.61 s spent in that
checkpoint. The table's import excludes it; Tantivy's commit is already within
its import. Query quantiles use 60 samples; under the recorded estimator p99
equals the observed maximum. These are not reliable production tail SLOs.

The [raw structural inspection](data/search-2026-10-16/storage-layout.json)
attributes a separate 100k post-churn FTS file by dbstat object and a Tantivy
directory by file. The measurement appendix reports that split; do not infer
the one-million-row object layout from a total file length.
Its first inspection failed because it assumed the directory byte count before
backend close must equal the post-close file sum. That failed attempt is retained
under `preflight/`; the corrected inspection records both points. Shutdown/file
retirement may change live space, so a directory capacity budget must also
consider active Searchers and merging, rather than only the final closed store.
The responsible mechanism is not causally isolated by this check.

Both implementations retain the parsed input corpus and scaled input documents.
RSS/HWM includes that materialization; it is not a minimum steady-state Search
memory requirement. CPU totals include integrity/reopen diagnostics, which
differ across backends and must not be treated as matched API CPU efficiency.
FTS full integrity scanning is not ordinary startup cost. The observed write
and RAM costs are already sufficient to reject a choice based on query/s alone.

## Small correctness/quality probes are not population measurements

Actual FTS5 callbacks pass source/index rollback, OLD-token update/delete,
signed SQL identity moves, string-key mapping, NFKC highlighting of original
UTF-8 bytes, rank-1 integrity and reopen with registration. A bare connection
fails on query execution with `no such tokenizer`; checking prepare alone was
an insufficient probe and its failed attempt is retained.

The original 20-document/18-query fixture shows: кошки/кошка and run/running
work in the stemmed candidate, while сталь/стали collides and человек/люди
does not match. The replication example retrieves only the lexical database
document, missing the derivational replication relation. Lowercase is not full
Unicode case folding: Straße/STRASSE and dotted-I need a deliberate policy.
The short German example also exposes unreliable language detection; short
query expansion alone does not fix a wrongly selected document stemmer.
Japanese/Thai probes exercise segmentation, not language-population relevance.

The post-timing namespace counterexample finds a separate, fixable encoding
defect in **both** backends: document text `s_ru_кошк` matches query `кошка`,
and `s_en_run` matches `run`, despite containing only an internal-looking
literal. Raw terms are unprefixed while stem aliases use those same strings.
This is a confirmed false positive on an explicitly judged four-document
fixture, not an assumption about unjudged natural results. Namespace **every**
term disjointly (for example raw `r|...` and stem `s|lang|...`) and rerun quality,
membership, phrase/offset and performance gates after that format change.
The frozen measured source remains unchanged to preserve reproducibility.

## Architecture candidates and acceptance boundary

| Candidate | Concrete implementation | Measured evidence / remaining cost |
|---|---|---|
| One SQLite Search backend | Owned documents + FTS5, plus same-file SQL projections; versioned shared Rust analyzer | Small deployment profile; atomic source/projection probes pass. Ranked query tails require explicit assessment, not a default claim of sufficient speed. |
| FTS5 for SQL, Tantivy owns standalone collections | Tantivy stores original key/title/body; Searcher pins matching documents and their fields | At 1m, query p99 47–68 ms versus FTS5 1145–1474 ms, store about 1014 versus 1778 MiB; process HWM about 2470 versus 1032 MiB and slower single SET. Adds a second backup/format/admission integration. |
| SQLite source + external Tantivy | Durable source outbox, committed watermark, idempotent replay and consistent-read barrier | Independent commits in the primary timing harness are not that protocol. Must not silently promise SQL snapshot semantics or quote SQL-only latency as a complete durable Search write. |
| Universal cross-engine Index Engine | Projections over arbitrary KV/SQL/Records/Metrics | No new evidence justifies it. Search does not require this scope. |

Implementation cost is lowest for the same-file FTS adapter because SQLite
already owns transaction, backup and recovery. A Tantivy-owned collection adds
writer scheduling, native/mmap accounting, file-format lifecycle and directory
backup/restore. A separately sourced Tantivy index adds an outbox, catch-up and
visibility protocol on top of those tasks. No schedule estimate is measured.

For a first release, implement the shared analyzer/definition contract and one
owner-approved storage contract with explicit language and resource targets.
SQL Search can start with FTS5 when its query budget fits. For the requested
read-oriented independent `store.search(...)`, take the Tantivy-owned prototype
forward to bounded-memory/grouped-commit/fault acceptance, rather than choosing
FTS5 automatically from its smaller executable. Generic cross-engine indexing,
semantic multilingual understanding and ANN are outside that first scope.

### Concrete prototype design to hand to Opus

Use one runtime-independent text-analysis library, with adapters for each
backend. The SQL adapter is an FTS5 C tokenizer, not an application-maintained
string of pre-tokenized text: query/document roles, colocated synonyms and
original UTF-8 offsets must survive the adapter. Bound input bytes, emitted
tokens, synonym count and query clauses before entering expensive native work.
Share immutable ICU/model data; do not allocate a language dictionary per
connection. The measured implementation materializes token vectors, so a
streaming implementation remains an engineering recommendation, not a speed
result from this round.

For **SQL projections**, keep source, stable identity mapping, FTS objects and
generation metadata in the source SQLite file. The managed writer updates
source and OLD/NEW postings in the same transaction; unrelated-column updates
skip tokenization. Publish visibility only after that commit. Register the
tokenizer on every connection and protect managed tables against direct writes.
This preserves a real SQLite snapshot instead of inventing an external-index
consistency promise. It does not make the measured long ranked queries cheap.

For an **independent Tantivy collection**, store original key and document
fields in Tantivy, index an exact key and use a numeric internal identity.
A single serialized collection writer performs delete-by-key plus add, groups
accepted operations, commits, reloads the reader and only then completes their
visibility promises. Each query pins one Searcher for scoring and field reads.
The prototype exercises this ownership boundary and individual/batched commits;
it does not implement TinyStore admission or a concurrent command scheduler.
Cancellation after admission cannot be described as a guaranteed rollback.
Operation-id reconciliation and acknowledged-prefix crash tests remain gates.

Do not introduce a SQLite source merely to wrap the independent store: that
would add a second commit and require the outbox/watermark protocol in the
third candidate above. Conversely, a SQL-table projection cannot inherit the
standalone collection's weaker cross-engine boundary by sharing its API name.

For **analysis/definition changes**, persist a versioned build manifest and
keep the previous generation readable until the replacement is complete.
Same-file FTS generations may use the earlier measured incremental backfill
and foreground dual maintenance, with identity moves and OLD tokens handled
transactionally. An independent store needs a pinned input snapshot plus an
ordered bounded mutation tail, or a durable canonical source/outbox. The
current owned-store experiment proves neither concurrent generation rebuild
nor crash-safe generation switching. Never update tokenizer behavior in place
and assume old postings now have the new meaning.

### Evidence boundary and product acceptance

| Category | Established here | Still required before shipping |
|---|---|---|
| Measured | Paired RU/EN/ZH relevance and latency; binary profiles; analyzer throughput; same-file write/read load; 100k/1m complete-store import, hydration and commit costs | Actual Core→Wire→SDK search, grouped commit scheduling, sustained churn and language-balanced large-scale queries |
| Correctness probes | Actual FTS registration, rollback, OLD-token maintenance, identity changes, original offsets, reopen/integrity; both stores' count/reopen diagnostics | Arbitrary keys/fields, duplicate concurrent SET/DELETE, savepoints, pinned-searcher lifecycle, format migration and managed-object protection |
| Architectural hypothesis | Shared bounded analysis, streaming tokens, grouped Tantivy commits, versioned generations and SQL/Tantivy split | Measure complete product paths before attributing a speed or memory improvement to any of these choices |
| Failure/resource gates | This round does not establish process-crash or power-loss safety of the new owned-store adapter | Kill at pre/post commit/reload/switch; compare acknowledged prefix and fresh rebuild; ENOSPC/OOM, long readers, corruption, backup/restore, cleanup after restart and cross-platform locks |

An acceptance run must use the product's fixed memory/disk/latency budgets,
include the input and retained-result buffers, measure native allocations and
copying, and keep writer progress under concurrent queries. This round records
RSS phases but does not isolate minimum idle/steady Search memory, allocations
per operation or bytes copied. A writer's configured Tantivy buffer is not a
global RSS cap. SQLite FULL on the lab filesystem is not a power-loss proof.

Same-file FTS source/content/postings writes amplify the future SQLite WAL
stream; the tables report actual WAL file high-water sizes. These are logical
file lengths with manual checkpoint boundaries, not block-device write bytes
or a measured replication bandwidth. Tantivy's zero SQLite WAL means its data
and metadata require another backup/replication format; it is not zero durable
I/O. No physical replication implementation is added or benchmarked here.

For both user-facing scenarios, keep an immutable analysis definition: Unicode
policy, segmenter/model/dictionary versions, language/morphology policy, indexed
fields and ranking configuration. Persist its hash with each generation. Register
the correct tokenizer on every relevant connection before schema use; a changed
binary must not silently reinterpret old postings. Build a new generation for
a changed analysis definition. The earlier generation/frontier/dirty-tail
research informs that lifecycle but does not prove a hard writer-time budget.

At pinned Core `76b844c`, the integration seam is
[`sqlite/connection.rs`](https://github.com/tinyshed/tinystore/blob/76b844cdc8c3410e746a5d5dc3e9aafec83c9962/crates/tinystore/src/sqlite/connection.rs):
writer, lazy reader pool, backup/copy and read-copy paths all need analysis
registration. Registration must precede operations that use the managed schema.
The Core authorizer, owned-object protection, grouped writer and native memory
admission are not automatically tested by this standalone CLI.

Owned collection keys need stable integer mappings for FTS5; SQL projections
need an explicit stable integer identity or a transactional mapping. Keep original
documents for display and future reanalysis. Do not require applications to store
stemmed text. Analyzer work currently materializes vectors and runs during FTS
write maintenance: product code needs streaming tokens, document/token byte
limits and writer/memory admission, with the complete commit in its budget.

Owner decisions: default supported-language quality contract; all/any/phrase
behavior and ranking; dynamic fields, nesting/types and weights; normalization
and stemming ambiguity; cross-engine transaction expectations; query latency
and memory targets; and whether standalone Search may use non-SQLite storage.
These are design decisions for implementation, not requests to approve research.

## Reproduce and interpret

[`search-lab/README.md`](../search-lab/README.md) and the
[raw ledger](data/search-2026-10-16/README.md) describe exact commands, revisions,
SHA-pinned corpus, feature profiles and two forward/reverse passes. Linux kernel
6.18.44, Xeon 8573C, 2-CPU quota, 6 GiB container; Rust 1.99.0, rusqlite 0.40.2
bundled SQLite 3.53.2, FULL WAL and 1 MiB native cache on a disk-backed volume.
These are native/analyzer/storage measurements, not Core→Wire→SDK rates,
production SLOs, power-loss guarantees or a replication implementation.
