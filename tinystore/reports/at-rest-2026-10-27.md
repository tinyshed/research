# At rest, v0.4.0 against v0.1.0 and the five services — 2026-10-27

The idle round of [the first release's](release-2026-10-23.md) again, on
TinyStore `v0.4.0` as npm publishes it, in the same image on the same machine:
every engine a small application uses opened and written once, then a minute
of rest; medians of three passes.

TinyStore got neither lighter nor faster at rest. Its server holds 16.7 MiB
where `v0.1.0` held 14.7, two MiB more, and is ready to serve, every engine
open, 0.135 s after it starts where `v0.1.0` took 0.133. The five services hold
402 MiB as they did, each within about a MiB of its figure four days ago, and
Loki is still ready last, after 15.4 s.

The ranges of the server's memory do not meet: the heaviest `v0.1.0` pass
held 14.7 MiB and the lightest `v0.4.0` pass 16.2. The times to ready differ by
less than one pass differs from another.

## Why it grew is not measured

The server's binary grew from 19.1 MB to 23.2 MB between the two releases, and
the library a program loads in process from 14.9 MB to 17.4 MB
(`@tinyshed/tinystore-linux-x64`, `bin/tinystore` and `lib/libtinystore_ffi.so`
as npm lists them). PSS counts the pages of the binary a process has touched,
and the page cache its case brought in grew by 3.2 MiB beside the 2.0 of PSS,
which fits more code mapped; it does not exclude a larger heap. run.py sums PSS
by process, not by mapping, so this round cannot divide the two MiB between the
binary's pages and anonymous memory. `/proc/<pid>/smaps` of each version's
server at rest, summed by mapping, would.

## What is different from the 2026-10-23 round

- **TinyStore.** `@tinyshed/tinystore@0.4.0` and its
  `@tinyshed/tinystore-linux-x64@0.4.0` from npm, installed at the round's
  start by `night.sh` with `TINYSTORE=0.4.0`; the lock it installed is in the
  data. `bench/idle.ts` is unchanged: no call it makes was renamed since
  `v0.1.0`.
- **The idle round alone**, `ROUNDS=idle`; `night.sh` learnt both settings
  for this round, and `versions.sh` now prints the server's own version.
- **No `v0.1.0` in the same run.** Its figures are the 2026-10-23 round's. A
  rerun of `v0.1.0`'s four cases beside this one was started and dropped at
  the owner's call; the services, measured again in this run, stand in for it.
- **The host was not idle.** Two Vite dev servers of TinyStore's docs site ran
  on Windows throughout, and an unrelated PostgreSQL container sat in the same
  Docker VM at 0 % CPU and 21 MiB. A first attempt, 12:51 to 13:07 UTC, ran
  while the docs site was built and tested on the host; it was stopped, and its
  13 finished cases are kept apart in `idle-overlapped.jsonl`, not in a median.
  Their memory fell within 1.4 MiB of the clean passes; their times did not:
  PostgreSQL was ready after 0.06 and 0.16 s, and the program's first calls
  to the services took 36 ms where they take 28.

The round ran 13:07 to 13:31 UTC.

## Reproduction

```sh
# from release-bench/, Git Bash: MSYS_NO_PATHCONV=1
docker build -t tinystore-release-bench .   # postgres:18-trixie moves; this round used the 2026-10-23 image
docker run --rm --init --privileged -v <release-bench>:/src:ro -v <results>:/results -v tinystore-release:/work \
  -e OUT=/results/<name> -e TINYSTORE=0.4.0 -e ROUNDS=idle tinystore-release-bench sh /src/night.sh
python3 summarize.py <results>/<name>
python3 compare.py 0.1.0=<research>/tinystore/reports/data/release-2026-10-23 0.4.0=<results>/<name> > compare.md
```
