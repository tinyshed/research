# Local leases: conditional SQL, contention and fencing — 15 October 2026

Follow-up: [actual Core grouped commits and lease correctness](core-locks-followup-2026-10-15.md)
supersede the integration assumptions here. Use the updated atomic-writer,
TTL and cancellation gates when implementing; these historical numbers remain unchanged.

The architecture to carry forward is authoritative SQLite state plus bounded,
resource-specific waiter admission. Avoid polling every waiter through the
single SQLite writer; broadcasting every release can replace a timer herd
with a notification herd. A grant becomes visible only after its transaction
commits. The memory gate in this round is an admission prototype, not a
replacement for persisted ownership or a distributed lock.

## Safety and failure evidence

The deterministic checks use injected integer times and verify expiry at the
exact boundary, rejection of an expired renewal even before takeover, stale
release/renewal rejection after takeover, extension without shortening TTL,
three concurrent permits with a fourth refused, reclamation of an expired
slot and a counter that survives closing/reopening SQLite.

Three uncommitted and three committed owner processes are killed with SIGKILL
after a flushed handshake. Recovery reopens SQLite and runs integrity_check.
Uncommitted ownership is absent and the first committed token is 1. A committed
owner is still held at time 105, expires at 110 and yields token 2. No cleanup
thread is needed for the acquisition predicate to reclaim an expired row.
These are process crash checks with injected clock values, not actual clock
jump tests, timed client/network death tests, power-cut tests or an HA proof.

The benchmark's monotonic origin is only valid within its fresh file/run.
A durable product cannot persist this relative origin across restart. It
needs the store's persisted-clock semantics, checked/saturating arithmetic
and a monotonic scheduling clock; a backwards wall-clock jump can otherwise
prolong ownership and a forward jump can expire it. Decide that behavior,
test it with the injectable Clock and report it to callers. A long writer
stall or COMMIT can consume most of a TTL before the grant is delivered;
the response must carry a deadline/remaining duration and reject an unusable
grant, rather than starting a fresh TTL on the client.

## Proposed authoritative state and algorithm

The proposed API starts with the caller's ordinary operation:

```ts
await store.locks.with('invoice/42', { ttl: '10s', wait: '2s' },
  async lease => {
    await writeToFencedSink({ token: lease.token, signal: lease.signal })
  })
```

This is an API sketch. Returning from the callback releases ownership;
automatic renewal can be a policy of the helper. A lost renewal aborts the
signal, but cannot forcibly stop arbitrary user code. Expose a lower-level
acquire/renew/release form for applications that need explicit ownership.
Timeout/cancellation means stop waiting, and a late grant must be released
or allowed to expire. A lost network response after COMMIT is ambiguous:
use a request identity/reconciliation path, never blindly assume no grant
was made. The SDK must not hide that ambiguity by retrying indefinitely.

Use internal tables rather than an ordinary user-expiring KV entry:

```text
resource(namespace, key, generation, next_fence, permit_limit)
slot(resource_id, slot_id, owner_nonce, fence, expires_at)
```

Within the file's one IMMEDIATE writer transaction:

1. Capture the authoritative time at execution; find an unowned/expired slot.
2. If none exists, return occupied and the earliest expiry without a write.
3. Increment the retained resource fence with overflow checked; assign an
   unpredictable owner nonce, slot, fence and expiry under the same transaction.
4. Reply only after COMMIT; keep cancellation/request identity until delivery
   is resolved. Never commit the counter separately from the slot.

Renew with `(resource, slot, owner, fence)` **and** `expires_at > now`, setting
`expires_at = max(expires_at, now + ttl)`. Renewing an expired lease is a new
acquisition, never resurrection of the old token. Release must compare the
same identity and cannot delete the retained fencing counter. Generic key
TTL, bucket clear, recreate and version reset are ABA traps. A counter is
not safe to garbage collect just because its latest lease expired. Resource
names/metadata require admission limits; choosing a safe tombstone lifecycle
is a separate design decision.

The probe scans a resource's small slot set (one or eight permits) and has
no expiry index. Do not extend that rate to an unbounded semaphore: either
bound the permit count or measure an index such as `(resource, expires_at,
slot)` and its extra WAL on every renewal. Client concurrency is not the
same dimension as permits per resource.

Fencing applies at the protected sink. For an exclusive resource, reject
tokens older than the last accepted resource generation. For a semaphore,
several grants are concurrently valid: a single global “largest token wins”
check would reject another still-valid holder. Scope the sink fence to a
stable slot/permit identity, or use a sink-side validator for active grants.
Shrinking capacity cannot recycle occupied slot identities. Send large
counters as an exact wire integer/SDK bigint or lossless string, not a JS
Number; never wrap on SQLite's signed 64-bit boundary.

An old backup can rewind a persisted counter. Define a store/restore epoch
and its sink-side registration before claiming fencing across restores.
A random new UUID alone is not a monotonically ordered HA term. Local
leases do not elect a new Primary and do not fence another server that
still runs: that requires an external authority/term accepted by the sink.

## Waiters and reuse of Jobs

Use a bounded FIFO wait list per resource and a heap/timer for the earliest
lease expiry. When release/expiry frees capacity, reserve eligibility for the
oldest waiter and schedule at most the available number of acquire attempts.
A new arrival must not steal the reservation. Remove cancelled/disconnected
waiters and transfer their reservation. Recheck SQL state after every wake;
notifications are hints, never ownership. Compare token/deadline generations
when discarding stale heap entries, bound those entries and periodically
compact them. Use a generation+registered-wait pattern to close missed-wakeup
races. A missed notification needs a bounded expiry fallback, not a permanent
sleep. These production scheduler details remain **unimplemented/unmeasured**;
the FIFO semaphore probe only measures the benefit of controlling admission.

A candidate to recover the lost grouping is **transactional handoff**:
the release command also conditionally assigns the just-freed permit to the
oldest still-live waiting request, in the same writer transaction. Reply to
both only after COMMIT. That can avoid a separate release-then-acquire sync
without polling every loser. Bound handoffs per batch, recheck waiter
deadline/cancellation at execution, and reconcile a grant whose response is
lost. This is a proposed optimization, not a speedup measured by `admitted`.

At the reviewed commit, `jobs/claim.rs::EXTEND_LEASE` compares id+attempt but
does not require the current `until > now`; `DROP_LEASE` also uses id+attempt.
That protects against another attempt's takeover, not against resurrection
before takeover. `jobs/engine.rs::from_file` calls `end_dead_leases`, which
counts dead attempts and deletes all rows when the engine opens. That matches
process-owned job handlers, not an external lease client whose TTL may still
be alive after a server restart. Completed/repeated jobs also do not provide
an eternally retained per-resource fencing counter.

Jobs' group occupancy is counted/claimed with its jobs in the same file;
jobs can live in jobs.db **or** an application SQL database. Moving those
permits to kv.db would require a cross-file transaction the architecture
explicitly does not have. Share a file-local lease/permit SQL primitive and
waiter machinery through SharedFile/Home; keep queue attempt accounting and
restart policy in Jobs. A public default lock can live in kv.db, while a
queue's internal permit lives beside the queue. Clarify whether a public
lock and a queue group with the same name are independent; do not silently
promise one global namespace across files.

## What follows

Build conditional ownership and exact token/deadline semantics first, then
targeted waiter admission, cancellation and SDK renewal. Integrate with the
product grouped writer and Jobs' file-local transactions before quoting
throughput. Gate the implementation on many-resource workloads, waiter
cancellation races, delayed commit/response, writer pressure from unrelated
KV, clock changes, restore epochs and end-to-end SDK reconnect behavior.
