# Rust kernels and SQLite feasibility — 2026-10-07

Experimental prototype measured locally. TinyStore source was unchanged at
`e307c48a40126aad0e2873b6bf3aaedef8115483`. The prototype was uncommitted and unpublished
when measured; content hashes pin the measured files in
[environment.json](data/rust-kernels-2026-10-07/environment.json). Publishing these
preserved artifacts does not make the run a formal committed-harness research

  without LTO overrides or native-CPU flags. Go uses `CGO_ENABLED=0`.
- Five Go/Rust pairs: G,R; R,G; G,R; R,G; G,R. Every reported calibration
  interval lasts at least 0.15 seconds. No builds or tests run during timings
  or RSS collection. This is a shared VM, not an isolated physical core.
- Collection started `2026-10-07T23:27:05.731616+00:00` and ended
  `2026-10-07T23:37:36.567517+00:00` UTC. Timings and allocation counters finished first;
  memory collection resumed with locally installed GNU time after the initial
  driver found that tool missing. No measured source or binary changed.
- 54 deterministic fixtures, warm input reuse. Metrics: 240 samples;
  records: 1024 integers; ingestion: 240 or 4096 arrivals. Xorshift, SplitMix64
  and LCG fixtures are generated by the prototype source, without a corpus.
  Counts, input fingerprints and every output byte agree between Go/Rust.
- Twelve tests per language passed, along with original Go codec, metrics and
  records suites. Rust formatting, Go vet and Python syntax checks passed.
  No product changes were made; full repository CI, race tests, other OSes and
  SDK checks were not run for this standalone research prototype.

## Speed

Medians in microseconds per owning-output operation. A ratio above 1 means
the Rust version is faster. These are selected algorithms, not Ingest/Read API
throughput. Samples' validation, labels, clocks, SQLite, locking, durability,
whole codec selection and records dictionary/FSE planning are excluded.

| Case                              | Go µs/op | Rust µs/op | Go / Rust |
| --------------------------------- | -------- | ---------- | --------- |
| ingest/ordered/4096               | 23.161   | 7.654      | 3.03×     |
| ingest/shuffled/4096              | 949.738  | 248.892    | 3.82×     |
| ingest/shuffled/4096/typed_sort   | 634.261  | 251.482    | 2.52×     |
| metrics/change/many/encode        | 6.068    | 3.995      | 1.52×     |
| metrics/change/many/decode        | 4.655    | 1.034      | 4.50×     |
| metrics/change/decimal/decode     | 1.870    | 0.455      | 4.11×     |
| metrics/change/raw/encode         | 1.448    | 0.568      | 2.55×     |
| metrics/packed/17/baseline/decode | 4.064    | 4.264      | 0.95×     |
| metrics/packed/17/chunked/decode  | 0.457    | 0.222      | 2.06×     |
| records/width_17/decode           | 9.156    | 6.110      | 1.50×     |
| records/width_17/decode_word      | 4.969    | 4.111      | 1.21×     |

Ordered preparation is 3.03× faster, shuffled preparation 3.82×, and the
selected change-value decoder 4.50×. The map/sort comparison also changes
standard-library implementation: Rust HashMap and typed unstable sort versus
Go's map and sort.Slice. Go's typed-sort variant cuts shuffled preparation from
949.74 to 634.26 µs; Rust remains about 2.52× faster against that variant.

The literal 17-bit residual decoder has no demonstrated improvement: medians
are close and pass ranges overlap. A word-reservoir algorithm changes the Go
decoder from 4.064 to 0.457 µs, an 8.89× improvement. That optimized Go decoder
is about 9.33× faster than the literal Rust decoder; optimized Rust is another
2.06× faster than optimized Go. Both algorithms preserve the same packed bytes
and validation checks. This separates an algorithmic gain from choosing Rust.

## Memory

Each fresh process retains approximately 64 MiB of identical logical output
after equal warmup. Go snapshots follow explicit GC. RSS includes executable
pages, stacks, retained allocator pages and harness overhead. These numbers
are post-construction observations, not steady-state engine memory limits.
All fixtures are constructed before filtering; unrelated closures are then
discarded. Baselines capture startup and fixture allocator effects.

| ingest/shuffled/4096       | rust | 65.57  | 1.61         | 65.52    | 64.00           | 0.03             |

Decoded buffers have equal capacities. Their RSS difference is modest:
69.54 versus 65.62 MiB for records and 74.52 versus 66.02 MiB for metric
changes. The harness itself retains larger Go metadata; this is reported
separately and is not a production-engine saving.

Preparation differs more: Go holds 80 MiB of array capacity for 64 MiB of
logical samples, versus Rust's 64 MiB. Growing slices and vectors follow
different policies. In the first Go shuffled-memory pass, live heap is 80.18
MiB while heap_sys is 155.78 MiB; post-GC RSS can still include available heap
pages. This supports separating live data from RSS. The experiment does not
isolate the effects of preallocation, GC tuning or allocator page release, so
it does not prove that an equivalent retained footprint is impossible in Go.

## SQLite feasibility

The [SQLite smoke](../sqlite-rust-spike/README.md) builds synchronous
`rusqlite = 0.40.1` with bundled SQLite, cache and limits features. SQLite is
linked into the executable: [ldd](../sqlite-rust-spike/evidence/ldd.txt) and
[ELF dependencies](../sqlite-rust-spike/evidence/readelf-dynamic.txt) show no
libsqlite3.so. Linux libc, libm, libgcc and the loader remain dynamic. A C
compiler is needed at build time; a fully static Linux artifact needs a
separate target/toolchain such as musl.

Both [4096-page](../sqlite-rust-spike/evidence/smoke-4096.txt) and
[1024-page](../sqlite-rust-spike/evidence/smoke-1024.txt) runs pass WAL,
foreign_keys, busy_timeout=5000, synchronous=FULL, fullfsync,
checkpoint_fullfsync, 1 MiB connection cache, 32 prepared programs,
query_only readers, BEGIN IMMEDIATE writer and deferred-reader snapshot
checks. They also check savepoint isolation, native SQLite value types,
SQLITE_LIMIT_LENGTH, disabled DQS/trusted_schema and no repreparation for
`LIMIT CAST(? AS INTEGER)`.

This proves configuration and linking feasibility, not a complete port.
Reader pools, grouped-write scheduling, cancellation/rollback, admission,
migrations, connection recovery and cross-platform VFS behavior remain.
Keep engine page sizes and cache differences, including KV's 4 MiB writer
cache; avoid changing FULL durability to manufacture a speedup.

Current TinyStore has SQLite 3.53.4 translated ahead of time from Wasm into
Go, with a Go VFS; there is no SQLite runtime Wasm interpreter in that stack.
The bundled smoke reports SQLite 3.53.2 with native Unix VFS. A future benchmark
must control the version and record build-option/VFS differences. Go's
THREADSAFE=0 applies to isolated translated instances and must not simply be
copied into a shared native C library. The smoke keeps THREADSAFE=1 and owns
each NO_MUTEX connection individually. Native SQLite malloc allocations bypass
Rust's allocator; use RSS plus SQLite memory/db-status counters for that round.

Rusqlite is the first candidate because its synchronous API maps directly to
this connection model. [SQLx](https://github.com/launchbadge/sqlx/blob/main/sqlx-sqlite/src/connection/mod.rs)
uses worker threads and channels for SQLite's async interface. Raw
libsqlite3-sys is rusqlite's underlying C binding, appropriate only for specific
API gaps. [Turso's compatibility document](https://github.com/tursodatabase/turso/blob/main/COMPAT.md)
currently lists gaps involving foreign_key_check, checkpoint_fullfsync and
WITHOUT ROWID mutation, which TinyStore uses. It is not a drop-in replacement
for these contracts.

## What follows

First evaluate the word-reservoir codec inside Go with production profiles.
Then compare one complete metrics or records path against a Rust/native-SQLite
candidate with the same schema, versions where possible, durability, cache
budgets, concurrency and errors. Match prepared-query behavior and preserve
transaction scheduling rather than checking pragmas alone.

The selected loops justify a further experiment; they do not justify a whole
rewrite yet. A 3× kernel improvement yields only 1.07× total speed if the kernel
accounts for 10% of execution, 1.20× at 25%, or 1.50× at 50%. The current public
API profile must establish that fraction. No total-engine speed or RAM saving
has been measured in this round.
