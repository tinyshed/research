# What an agent's socket weighs, and what ten agents do through a proxy

**6 November 2026.** Plan chapter 8's third round agreed on agents for slice 7 and asked for a spike before its
code: the weight of a WebSocket and of TLS in Dashbin's static binary, and ten agents end to end — a call there
and back, a cancel, a lost hub, a slow link, restarts and memory. Measured with
[agent-probe](../agent-probe/): `weigh/` builds Dashbin at `a8ef861` with each variant, and `probe/` is a
prototype of the chapter's hub and agent that reads through Dashbin's own `postgres` and `mysql` plugins at that
commit. Windows 11, Docker Desktop 29.6.2; every output as it printed is in
[data/agent-2026-11-06](data/agent-2026-11-06/).

Each section says what was run, what it showed, and what it decides; the last section gathers them.

## The weight

Each variant is Dashbin's binary with a harness that uses what it links, built static for musl in
`dashbin-musl:1.99.1` as `just size` builds (`weigh/run.sh`); none names a library to load.

| Variant                                                     | Bytes      | Over Dashbin |
|-------------------------------------------------------------|------------|--------------|
| Dashbin at `a8ef861`                                        | 8 495 536  |              |
| the hub's side: axum's `ws`                                 | 8 663 472  | +167 936     |
| the agent's side, no TLS: tokio-tungstenite 0.29            | 8 622 512  | +126 976     |
| the agent over rustls 0.23 on ring, Mozilla's roots inside  | 9 957 840  | +1 462 304   |
| the agent over rustls on ring, the system's roots           | 9 920 976  | +1 425 440   |
| the agent over rustls on aws-lc-rs, Mozilla's roots inside  | 12 092 112 | +3 596 576   |
| both sides, rustls on ring, the system's roots              | 10 093 008 | +1 597 472   |

- **One tungstenite serves both sides**: axum 0.8.9's `ws` is tokio-tungstenite 0.29, and so is the agent's
  client; `cargo tree -i tungstenite` shows one copy.
- **ring keeps aws-lc out**: tokio-tungstenite's `__rustls-tls` takes rustls without its default provider, and
  rustls with `ring` alone links no aws-lc. aws-lc-rs weighs 2.1 MB more than ring for the same client.
- **The system's roots are read at run time**, from the files of a Linux server's CA bundle, and weigh 36 864 bytes
  less than Mozilla's compiled in; a server with no bundle needs `tls.ca`.

## Ten agents through Caddy

`probe/compose.yaml`: PostgreSQL 18, MySQL 8.4 and MariaDB 11 on a network `lan`; the hub's prototype on `wan`
behind Caddy 2.11.9, which holds TLS with its own CA (`tls internal`); ten agents on both networks, five beside
PostgreSQL, three beside MySQL, two beside MariaDB, each dialling `wss://hub.probe/api/v1/agent` with that CA.
The driver runs on the host and reaches the hub's port straight, as a command line on the hub's machine would; the
agents reach it only through Caddy. The prototype speaks chapter 8's slice 7 protocol: a greeting with the
agent's name, a call, its frame as one JSON message, its error, `$cancel`; the hub pings every 15 s and lets a
connection go after 45 s of silence.

### A read there and back

| Path                                                   | Median of     |      |
|--------------------------------------------------------|---------------|------|
| host → hub → Caddy's TLS → agent → database, `select 1` | 300, ten sites | 3 ms |
| host → PostgreSQL through Docker's port, the same read  | 30            | 3 ms |

The agent opens a connection to its database for each read, as Dashbin's plugins do; inside Docker that is cheap,
and across a real network each hop costs its round trip. Every time here is Docker's loopback.

### Identity

- **A token pasted onto the wrong agent is refused at the greeting**: `token-site1` saying it is `site2` was closed
  with "this token is site1's, and the agent says it is site2"; a token no agent has was refused 401 before the
  socket opened; the real `site1` and `site2` stayed connected through both.

### A cancel

- **A command line that leaves stops the statement in 4 ms**: half a second into a 30 s sleep the driver closed its
  HTTP connection; the hub dropped the call and sent `$cancel`, the agent dropped the plugin's read, and the
  statement was gone from PostgreSQL's, MySQL's and MariaDB's process lists 4 ms after, on each.

### A lost hub

The agent `site2` was cut from `wan` 0.8 s into a 28 s sleep, its database still beside it.

- **The hub noticed in 41.8 s** — 45 s of silence counted from the last bytes, a ping's answer a few seconds
  before the cut — and the read answered 503 "the agent went away" after 42.6 s.
- **The statement ran to its own end**, 27 s after the cut: 45 s of silence is longer than any read's bound of
  30 s, so on a silent cut a SQL statement ends by its bound (SRC-03) before either side notices.
- **Mended, the agent was back in 3 s**, and nothing it had been running was sent again.

### A slow link

The agent `site5`'s link to the hub was slowed to 1 Mbit/s with `tc netem` while it answered 10 000 rows of
1 000 characters, about 10.1 MB of `FrameJson`; every 5 s the driver also read `select 1` on `site1` and on
`site5`, the latter given 5 s.

| The hub's liveness                 | The big answer               | `site1`'s reads meanwhile | `site5`'s own small reads                |
|------------------------------------|------------------------------|---------------------------|------------------------------------------|
| bytes: silent when no byte arrives | 200 after 84.6 s             | 4–5 ms, every one         | 504 after 5 s each, until the big one was through |
| messages: silent when no message ends | 503 at 41.6 s, the agent let go as silent | 5 ms, every one | 504, then 503 once the agent was gone |

- **A long message is a live peer only if bytes count**: a WebSocket library hands over a message once it is whole,
  so a hub that counts messages lets an agent go while its answer is still arriving. The probe watches the socket
  under the WebSocket (`src/watched.rs`), which axum's `ws` does not expose, so its hub upgrades the request itself
  over hyper, about thirty lines.
- **A frame sent whole holds its agent's other answers behind it**: the agent's small answers waited until the big
  one had crossed, and timed out. Other agents were not touched. At 1 Mbit/s the agent's bytes ceiling of 16 MiB is
  two minutes on the wire, at 10 Mbit/s thirteen seconds.

### Memory

| Agent          | Resident, idle | Peak, four reads of 10 000 rows at once |
|----------------|----------------|-----------------------------------------|
| beside PostgreSQL | 4 780 KiB   | 11 700 KiB                              |
| beside MySQL   | 4 580 KiB      | 12 408 KiB                              |

The probe's agent runs on musl's allocator; Dashbin's agent mode, jemalloc with its decay at zero, is not measured
here.

### Restarts

- **The hub killed and started again**: the ten agents were back 1.14 to 1.30 s after the restart began, spread by
  their jitter of a fifth of a 1 s wait.
- **A reload of Caddy closes every agent's socket**, with the same configuration forced or a changed one: ten
  disconnected each time. With `stream_close_delay 10m` in the `reverse_proxy` of the configuration being
  replaced, a reload closed none, and none when it went back to the plain one either.
- **Short connections in a row grow the wait to 30 s**: a connection that lasts under a minute doubles the agent's
  wait, so after a Caddy recreated and three reloads within two minutes each agent took 30 s to come back.

## What it decides

1. **tokio-tungstenite 0.29 on both sides, rustls on ring, the system's roots with `tls.ca`**: +1 597 472 bytes,
   10 093 008 in all; aws-lc stays out.
2. **Liveness is bytes read**: the hub, and the agent for symmetry, count a connection silent when no byte has
   arrived for 45 s, from a watched socket under the WebSocket, so the hub's door does its own upgrade over hyper.
3. **The agent's wait starts over once the hub welcomed it**, not after a minute: a refused or failed dial still
   doubles it, and a reload of a proxy costs a second, not thirty.
4. **The recipe for Caddy sets `stream_close_delay`**, and says that without it every reload drops every agent for
   their wait.
5. **The bytes ceiling decides how long one agent's other panels may wait behind its biggest answer** on a slow
   link; its default is for Dmitry to set. 16 MiB is two minutes at 1 Mbit/s; 4 MiB is about thirty seconds and
   still holds 10 000 rows of a dozen short columns. Frames that stream, later, end the wait.
6. **A silent cut needs nothing more**: a statement ends by its own bound before the cut is noticed, and the
   agent's dropping of its calls matters to a call without one.

**Left open**: an agent behind a corporate HTTP proxy, a hub behind Cloudflare Tunnel, a real network rather than
Docker's loopback, Dashbin's agent mode with jemalloc, and hundreds of agents, whom a jitter of 200 ms at a 1 s
wait does not spread.

## Commands

```sh
# the weight: a detached worktree of dashbin at the commit weighed, every variant in turn
git -C <dashbin> worktree add --detach <tmp>/weight-tree a8ef861
sh agent-probe/weigh/run.sh <tmp>

# ten agents: build the probe in a worktree of dashbin, start its world, drive it
git -C <dashbin> worktree add --detach <tmp>/probe-tree a8ef861
sh agent-probe/probe/build.sh <tmp>
<tmp>/agent-probe-driver.exe drive
PROBE_LIVENESS=messages docker compose -f agent-probe/probe/compose.yaml up -d hub
<tmp>/agent-probe-driver.exe drive overload
```

The first full run printed each answered read as "null rows", a mistake of the driver's in reading `FrameJson`;
the statuses are the hub's, and the second run counts rows.
