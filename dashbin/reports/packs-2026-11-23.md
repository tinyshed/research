# What a pack's tables and icons cost a hub

23 November 2026. Stand: [`pack-probe/`](../pack-probe/). Dashbin at `0e39763`; nothing of Dashbin was built
for this. Raw output: [`data/packs-2026-11-23/`](data/packs-2026-11-23/).

**The question.** A pack is to be tables, files and dashboards put on a hub by a command: a table of a key and
its fields, found exactly, by a domain's suffix or by an address's range. Can a hub hold the tables people
would bring, the domain lists and the address ranges of a VPN's world, as plain text loaded into memory, or do
they need a format, an index or a library?

**The answer.** Text for a person to write, bytes for a hub to hold. Read as text into a first and a last
address a range, the largest table, 733 thousand ranges, loads in 69 ms and keeps 17 MiB. Written once as
bytes, a start a range, it loads in 1.3 ms and keeps 5 MiB, and answers in 39 ns either way: a showing's
10 000 rows are 0.4 ms. The domain lists are a megabyte. Nothing here asks for `mmdb`, protobuf or a crate.

A domain is looked up as its whole name, then each suffix at a label: a hash map probes once a suffix, a
sorted text halves once a suffix, eight times slower and half the memory. Either is far inside a showing.

The ranges are two sorted columns a family, the first address halved over. 369 037 of the 369 798 v6 ranges of
the country table begin and end on a /64, so half their bytes are zeros: a hub that minded 17 MiB could keep
9. It need not: a table is loaded when a read first names it and can be let go.

## The same tables held small

Dmitry's objection to the first table: 17 MiB to walk a table of countries is too much. `compact.rs` keeps a
range's start alone, since a range ends where the next begins and a gap is a range of no value; a v6 start as
its upper half, the 761 ranges that are not whole /64s in a list of their own; a value's number in the one to
three bytes the table needs; every value in one text. `probed.rs` keeps the domains' keys in one text with
slots over it. Each was checked to answer a million lookups as the first table does.

| Table                            | File KiB | Gzipped KiB | Load ms | Held KiB | Lookup ns |
|----------------------------------|---------:|------------:|--------:|---------:|----------:|
| country, a first and a last      |   31 724 |       4 534 |    69.0 |   17 259 |        38 |
| country, starts, read from text  |   31 724 |       4 534 |    83.1 |    5 363 |        39 |
| country, starts, read from bytes |    5 045 |       1 424 |     1.3 |    5 054 |        39 |
| asn, a first and a last          |   30 134 |       6 868 |    69.5 |   12 191 |        38 |
| asn, starts, read from text      |   30 134 |       6 868 |    78.5 |    8 492 |        46 |
| asn, starts, read from bytes     |    7 739 |       2 984 |     2.2 |    7 742 |        46 |
| domains, a hash map              |    1 046 |         244 |     5.9 |    2 293 |        92 |
| domains, one text and slots      |    1 046 |         244 |     2.9 |    1 091 |       153 |

The time to load was the parsing of addresses, not the reading: bytes load fifty times faster. So a hub
compiles a table once, when the pack is added, and keeps the bytes; the text stays what a person writes and a
repository diffs. Of the 7.7 MiB of the owners' table, 83 thousand names are the larger part.

## A pack kept in TinyStore

`stored`, the probe's second binary, with TinyStore 0.11.0, its `sql` and `blobs` features, every commit
synced to the disk as a hub's is. A pack is a set of files inside the hub's database, `db.files("packs")`,
so that it commits with the row that names it: a file of 16 KiB or less stays in the database's file, a larger
one is a file of its own beside it.

| What                                              |   Count |    ms | Each     |
|---------------------------------------------------|--------:|------:|---------:|
| `simple-icons` put, one transaction               |   3 475 |   282 | 81 µs    |
| icons put, a transaction each                     |     200 |   311 | 1 557 µs |
| `country.bin` put, 5 045 KiB                      |       1 |   9.2 |          |
| `asn.bin` put, 7 739 KiB                          |       1 |  11.8 |          |
| icons read whole                                  |   3 475 |  25.2 | 7.3 µs   |
| the store opened again                            |       1 |   0.1 |          |
| `country.bin` read whole, its SHA-256 checked     |       1 |   3.0 |          |
| the table made of those bytes                     |       1 |   0.6 |          |
| `asn.bin` read whole and made a table             |       1 |   5.4 |          |

A pack of 3 475 icons and three tables is on the hub in a third of a second, in one transaction; a transaction
a file is twenty times slower a file, so a pack goes in whole. A table is ready 3.6 ms after a read first
names it, 3.0 of them the SHA-256 TinyStore checks. An icon is read in 7 µs. The directory held 27 MiB for
18.7 MiB of files while the journal was not yet folded in.

**The other way: rows the store looks up, nothing in memory.** The same domains and the v4 countries as SQL
rows, a lookup a statement.

| Table            | Insert, one transaction | Disk    | Lookup in rows | Lookup in memory | In memory |
|------------------|------------------------:|--------:|---------------:|-----------------:|----------:|
| domains, 40 843  |                   79 ms | ~2 MiB  |         8.3 µs |           153 ns |   1.1 MiB |
| v4 countries, 362 998 |             667 ms | ~8 MiB  |         3.5 µs |            39 ns | 5 MiB with v6 |

Rows keep no memory and cost a hundred times the lookup: a showing's 10 000 rows are 35 to 83 ms where a table
in memory takes 0.4 to 1.5. Both are inside a showing; memory is the one a person would not notice.


## What the first slice cost the binary

Dashbin at `c6d693b`, the slice that keeps packs, against `0e39763` before it; static
`x86_64-unknown-linux-musl`, fat LTO, one codegen unit, Rust 1.99.1, in the image `just size` builds in, no
page carried in either.

| Build                                                   |      Bytes | Over the first |
|---------------------------------------------------------|-----------:|---------------:|
| before the slice                                        | 13 997 168 |                |
| before, TinyStore's `blobs` feature on and never called | 13 993 072 |         −4 KiB |
| after the slice                                         | 15 181 104 |     +1 156 KiB |

A feature that is on and not called costs nothing: TinyStore reaches its files from nowhere of its own. Two
programs of `pack-probe/weigh/`, one keeping rows as a hub did and one keeping a pack's files beside them with
the calls `store/packs.rs` makes, differ by 560 KiB.

The same two builds with their symbols kept, `nm -S --size-sort -C`, the growth by the crate a symbol names
first: 976 KiB of the 1 156 is in symbols.

| Crate               | Grew    | What it is                                                              |
|---------------------|--------:|-------------------------------------------------------------------------|
| `tinystore`         | 468 KiB | its files: reads and writes, and `scrub`, `recover`, `maintain`, `trim` |
| `dashbin`           | 258 KiB | the slice's own code: `sayings`, `put_pack`, `load_packs`, `Pack::read` |
| `core` and `alloc`  | 178 KiB | what that code and its serde types instantiate                          |
| `serde_json`        |  32 KiB | `Manifest`, `KeptPack`, `PackSent` read and written                     |
| `tokio`             |  18 KiB |                                                                         |

So two fifths is the store's files and about as much the slice itself, an async function at 20 to 35 KiB and a
derived `Deserialize` at 13 to 20. Nothing in it is a library taken by mistake.

## The same tables in Dashbin, on a hub

Dashbin's working tree after `c6d693b`, the slice that looks values up, `cargo build --release`, Windows 11,
the same machine. A pack `geo` of v2fly's domains, 40 843 keys found by suffix, and DB-IP's countries, 732 796
ranges, 32 MB of text; a hub on loopback with nothing else kept.

| What                                                        | Measured            |
|-------------------------------------------------------------|--------------------:|
| `dashbin pack add geo`, checked here and put whole          |              455 ms |
| the hub's memory, empty, then with the pack                 |   12.6 MB → 22.5 MB |
| a read of six rows with two lookups, through `/api/v1/run`  |              1.3 ms |
| the hub opened, nothing kept                                |                6 ms |
| the hub opened with the pack kept                           |    111 ms to 128 ms |
| of that, the pack read from its text                        |               80 ms |

The pack costs the hub 10 MB, the domains' hash map and keys and the ranges together, and a tenth of a second
when it opens: every table's text is read from the store, 30 ms with the SHA-256 the store checks, and parsed,
80 ms, two addresses a line. The first cut of the reader took 120 ms: it cut every line into a vector of cells,
where only a line whose set of fields is new needs one. Bytes written once when a pack is added load in 1.3 ms
in the probe and are not built.

**A number that was wrong.** The hub's start was first timed from a shell as the time until `curl` got an
answer, and came out as 92 ms with nothing kept and 610 ms with the pack. The 610 was Windows: a connection to
a port nothing listens on yet takes half a second to be refused there, so a hub that was 100 ms late read as
500 ms late. The figures above are `Hub::open` timed inside the process, `--release`.

A pack is sent as one JSON document of 64 MiB at most: DB-IP's countries and its owners together, 62 MiB of
text, pass it once their tabs are escaped, and go as two packs.
