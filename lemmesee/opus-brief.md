## Контекст

Прочитай `../AGENTS.md`, `README.md`, `plan.md`, новый обзор выше и
`../dashbin/plan/11-api.md`, `../dashbin/plan/14-first-version.md`.
Первый обзор `reports/literature-2026-10-27.md` предварительный; новый
уточняет его выводы о новизне.

lemmesee — исследование для `dashbin see`: подключиться к незнакомой БД,
предложить несколько полезных панелей, обозначить догадки и сохранить
подтверждённый человеком смысл. В production нет LLM, Python и inference
runtime. Генератор создаёт кандидатов из ограниченных шаблонов; правила
или маленькая модель ранжируют их. Бизнес-смысл, валюту, единицы и правила
признания оплаты нельзя выдавать за установленные по имени колонки.

План сравнивает A: схема + правила; B: схема и существующие статистики +
правила; C: те же данные + компактный обученный ранкер; D: ограниченная
выборка, когда она оправдана. Пока ничего не запускалось и не измерялось.
Весам задан исследовательский ориентир 256 KiB, дополнительной памяти —
1 MiB; это не доказанные результаты. Продуктовые пороги Dashbin отдельные:
в главе 14 есть лимит 2 MiB добавки к бинарнику, время на колонку и пороги
полезных/вредных панелей. Не смешивай эти бюджеты.

## Что уже стоит учитывать

1. **Ближайший практический аналог — Metabase X-rays.** У него уже есть
   шаблоны дашбордов, связывание полей с ролями, метрики и баллы кандидатов.
   Нужен сильный baseline на правилах с явно названными входами.
   [Код и объяснение алгоритма](https://github.com/metabase/metabase/blob/9f81a6dea2bc240f5e41000f14a25d298ff5d7ed/src/metabase/xrays/automagic_dashboards/core.clj).
2. **SeeDB уже рассматривает snowflake-схемы и joins.** Многотабличность
   сама по себе не новая. Его предпосылки о dimensions/measures и заданной
   пользователем выборке отличаются от нашего холодного старта.
   [Статья, §2](https://www.vldb.org/pvldb/vol8/p2182-vartak.pdf).
3. **ScaleViz уже выбирает признаки при бюджете и начинает с zero-cost
   features.** Проверяй отличие по конкретным входам, цели и полной цене
   адаптации. Близость к ответам полной модели не равна полезности человеку.
   [Метод и оценка](https://arxiv.org/html/2411.18657v1).
4. **«Каталог» не означает «никаких значений».** В `pg_stats` есть значения
   и границы гистограмм. Сначала зафиксируй скалярный allowlist. PostgreSQL
   `correlation` описывает физический порядок строк, не связь суммы с датой.
   У MySQL другой набор возможностей; отсутствие статистики — отдельное
   состояние, а не ноль.
   [PostgreSQL 18](https://www.postgresql.org/docs/18/view-pg-stats.html),
   [MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/optimizer-statistics.html).
5. **Цена рекомендации и цена данных для панели различны.** Схема позволяет
   предложить count по дням, но точная агрегация может просмотреть всю таблицу.
   Даже PostgreSQL TABLESAMPLE BERNOULLI сканирует таблицу целиком.
   [COUNT](https://www.postgresql.org/docs/18/functions-aggregate.html),
   [TABLESAMPLE](https://www.postgresql.org/docs/18/sql-select.html).

Новизна комбинации «существующие статистики + компактная offline-модель +
цена на стороне БД + отказ от неподтверждённого смысла» остаётся гипотезой.
Не превращай «не нашли» в «этого никто не делал». Детали чтения и границы
проверки указаны в обзоре; это не полный систематический обзор литературы.

## Задание

Подготовь конкретную спецификацию первого пилота A/B и минимальный
исследовательский каркас. Модель и обучаемую стратегию выборки выбирай
после появления размеченных ошибок правил.

Нужны следующие результаты:

- **Контракт получения признаков для PostgreSQL и MySQL:** таблица
  «признак → точный источник → нужны ли значения → доступность/свежесть →
  возможная работа на сервере». Начни со скалярных статистик, без обновления
  ANALYZE. Отдельно опиши discovery, preview и исполнение сохранённой панели.
- **Одна спецификация кандидатов для обеих конфигураций:** роли колонок,
  агрегат, grain строки, путь join, время/таймзона, единицы, происхождение
  каждого вывода и причина отказа. Не считай SUM безопасным только потому,
  что SQL-тип числовой. Предложи, как ограничить дублирующие панели в top-5.
- **Маленький публичный пилот:** ориентир 8–12 схем, примерно 10 кандидатов
  на схему, два судьи. Это предложение для отладки процедуры, не финальная
  статистическая мощность. Назови источники, версии, лицензии, способ
  загрузки и будущие хеши; корпуса не коммить. Схемы нужны разные, в том
  числе без FK и с отсутствующими/устаревшими статистиками.
- **Форма разметки:** отдельно «оставил бы», «смысл подтверждается», «смысл
  неверен», «не хватает сведений», «нужен человек/может помочь выборка».
  Оценивай панель вместе с заголовком, SQL и областью данных. У судьи должна
  быть опора для проверки предметного смысла; слепое угадывание по схеме
  не создаёт ground truth.
- **Набор контрпримеров:** fanout `orders → order_items`, несколько валют,
  балансы по снимкам, импорт вместо даты события, неоднозначные статусы и
  маскированные имена. Для каждого покажи ожидаемый отказ или корректный
  ограниченный вывод. Выборка не должна обещать решить отсутствие бизнес-правила.
- **Протокол сравнения:** общий пул кандидатов, скрытый от судьи метод,
  перемешанный порядок; полезность top-5, вред среди показанных и среди
  оставленных, coverage и интервалы неопределённости. Отдельно проверь,
  какие полезные вопросы генератор вообще не умеет выразить. Не сравнивай
  методы только по NDCG и не награждай отказ от всех панелей.

Для следующих раундов оставь понятные интерфейсы: снимок признаков →
кандидаты → оценки → набор панелей → решения человека. Подтверждение смысла
должно иметь область действия и правило устаревания при изменении схемы.
Разделение train/test — по исходным проектам и семействам схем, с поиском
копий, миграций и форков. Существующие графики и SQL-вопросы не заменяют
разметку полезных панелей; SchemaPile не содержит готовых живых pg_stats.

Первый результат должен позволить решить: полезны ли правила, чего не
хватает в метаданных, и есть ли вообще ошибка, которую способен исправить
маленький ранкер или дополнительная выборка. Ответ «правил достаточно»
считается полноценным успехом исследования.

Соблюдай `measure`. До реальных замеров harness должен быть закоммичен по
правилам репозитория; самостоятельно коммитить и пушить без просьбы нельзя.
Подготовку каркаса и статическую проверку делай без подключения production
и без объявления результатов замеров.
